# 前言

这份笔记面向长期维护的大语言模型知识库，目标是沉淀一条可以反复查阅、持续更新的学习路径。它最初整理自 `datawhalechina/diy-llm` 的文档，之后持续吸收 Stanford CS336、公开论文、模型技术报告和工程实践。

LLM 的技术栈很宽：分词器、Transformer 架构、优化器、数据工程、CUDA kernel、分布式训练、scaling laws、推理系统、评估和后训练都会彼此影响。只从 API 或榜单看模型，容易把这些层次压成一个不可检查的整体；更能迁移的理解，通常来自对底层机制和资源约束的把握。

## 笔记关注什么

能跨越模型规模迁移的知识可以分成三类，这三类也决定了各章的取舍：

- **Mechanics**：组件到底如何工作，例如 BPE 如何合并、Transformer 如何计算、ZeRO 如何分片、PagedAttention 如何管理 KV cache。
- **Mindset**：如何把硬件的算力、显存和带宽用满，并且认真对待规模——小尺度上得到的结论要能说明它在放大后如何变化。
- **Intuitions**：哪些架构、数据和训练技巧可能有效。

三类取舍的边界可以按下面这张表对照读：

| 类别 | 解答什么 | 跨规模是否稳定 | 落到哪类小节 |
| --- | --- | --- | --- |
| Mechanics | 「这一步具体怎么算」 | 稳定 | 各章机制与公式小节（[第 1 章 分词器](chapter1/chapter1_分词器.md)、[第 3 章 语言模型架构和训练的技术细节](chapter3/chapter3_语言模型架构和训练技术细节.md)、[第 5 章 GPU 和 GPU 相关的优化](chapter5/chapter5_GPU和GPU相关优化.md)、[第 7 章 分布式训练](chapter7/chapter7_分布式训练.md)、[第 9 章 推理系统](chapter9/chapter9_推理系统.md) 等） |
| Mindset | 「这一层硬件资源有没有用满」 | 稳定 | [第 2 章 PyTorch 与资源核算](chapter2/chapter2_pytorch与资源核算.md) 资源账本、[第 5 章 GPU 和 GPU 相关的优化](chapter5/chapter5_GPU和GPU相关优化.md) roofline、[第 7 章 分布式训练](chapter7/chapter7_分布式训练.md) collective 与并行策略、[第 9 章 推理系统](chapter9/chapter9_推理系统.md) serving scheduler |
| Intuitions | 「这个设计选择是否值得尝试」 | 受规模、模型尺寸和数据配比影响 | [第 3 章 §3.3 超参数考量与设计原则](chapter3/chapter3_语言模型架构和训练技术细节.md)、[第 8 章 §8.6 Scaling in Practice：MiniCPM、DeepSeek 与现代报告](chapter8/chapter8_Scaling_Laws.md)、[第 12 章 大模型的基本训练流程](chapter12/chapter12_大模型基本训练流程.md)、[第 13 章 可验证奖励的强化学习（RLVR）](chapter13/chapter13_可验证奖励的强化学习.md) |

第四列是查找入口：想确认某个组件具体怎么算，从 Mechanics 行列出的章节进入；想核对一层硬件资源有没有用满，从 Mindset 行进入；想看某个设计选择在什么实验设置、数据配比和训练预算下成立，从 Intuitions 行进入。

前两类在不同规模上稳定成立，可以写成能反复复核的机制和资源账本。Intuitions 的结论常常绑定在具体的模型尺寸、数据配比和训练预算上，换一个尺度就可能翻转。章节因此优先沉淀 Mechanics 与 Mindset，把 Intuitions 写成带实验设置和适用区间的案例。涉及具体模型、论文、硬件规格、评测结果或厂商声明时，按 [STYLE.md](../STYLE.md) 的来源与日期约定记录，不另设专门目录。

以下几条判断贯穿各章。每条主题都给出章节定位，方便回头查找：

- **Leaky abstraction**：PyTorch、CUDA、NCCL 和集群调度每一层都提供了简洁接口，但规模变大后，下层的显存容量、带宽和通信拓扑会穿过接口显现在训练曲线和吞吐上。各章因此把抽象边界上的资源账本写清楚，让读者在每一层都能查到具体的 FLOPs、HBM 带宽、通信量、显存开销与质量 trade-off。具体落点见 [第 5 章 GPU 和 GPU 相关的优化](chapter5/chapter5_GPU和GPU相关优化.md) 的资源账本、[第 6 章 GPU 高性能编程](chapter6/chapter6_GPU高性能编程.md) 的 kernel / PTX / Triton 视角、[第 7 章 分布式训练](chapter7/chapter7_分布式训练.md) 的 collective 通信拓扑，以及 [第 9 章 推理系统](chapter9/chapter9_推理系统.md) 的 KV cache 与 serving scheduler。
- **Bitter lesson**：Richard Sutton 在 *The Bitter Lesson*（2019-03-13）里给出的结论是，能利用算力的通用方法在长期最有效，其中 search 和 learning 是两类可以随算力任意放大的方法。落到工程判断上，问题就变成哪些算法能随规模继续放大：哪些技巧在大规模下仍稳定，哪些只在 small-scale 实验里成立。该判断作为尺度选择的背景，落到 [第 8 章 §8.1 Scaling Workflow：先拟合，再放大](chapter8/chapter8_Scaling_Laws.md) 的「先拟合、再放大」流程与 [第 8 章 §8.6 Scaling in Practice：MiniCPM、DeepSeek 与现代报告](chapter8/chapter8_Scaling_Laws.md) 的 MiniCPM / DeepSeek / muP 讨论中。
- **效率框架**：各章反复使用的框架写成 $\text{accuracy}=\text{efficiency}\times\text{resources}$ 。 $\text{resources}$ 指投入总量，包括总数据、总算力、总显存和总通信； $\text{efficiency}$ 指单位资源换到的模型质量。规模越大 efficiency 越关键，因为资源总量拉满之后只能靠提高单位资源的产出继续前进。评估一项新技术时，先看它改善的是哪一项，再看两者的乘积是否真正上升。具体落点见 [第 8 章 §8.3 LLM 的 Scaling Behavior](chapter8/chapter8_Scaling_Laws.md) 与 [第 8 章 §8.4 Joint Scaling：模型、数据与计算](chapter8/chapter8_Scaling_Laws.md)，以及 [第 11 章 评估与基准测试](chapter11/chapter11_评估与基准测试.md) 关于 perplexity 与 exam / chat / agent / reasoning / safety 基准的章节。
- **44× 算法效率**：在 ImageNet 上把分类器从头训练到 AlexNet 级别精度所需的浮点运算量，在 2012-2019 年间下降到原来的 1/44，相当于算法效率每 16 个月翻一倍；同期摩尔定律给出的硬件效率提升约 11 倍。这些收益被归因于 sparsity、batch normalization、residual connections、architecture search 和合适的规模缩放。这个数字给出了 efficiency 一侧还有多大空间；一个架构或训练改动究竟改写 loss 曲线的 offset 还是 slope，落在 [第 8 章 §8.3.4 Model Scaling 与 Architecture Scaling](chapter8/chapter8_Scaling_Laws.md)。
- **SwiGLU 与 "divine benevolence"**：带门控的 FFN 变体（GEGLU、SwiGLU、ReGLU）在 T5 式的预训练设置里给出一致更低的困惑度，在多数下游语言理解任务上也更好，之后被 LLaMA、PaLM、Qwen 等模型族沿用。Noam Shazeer 在 *GLU Variants Improve Transformer*（arXiv:2002.05202）的结论一节里写道，作者对这些结构为什么有效不作解释，把它们的成功"和其他一切一样，归于 divine benevolence"。这类只有经验支撑的架构选择，各章按实验设置和观测差值呈现。具体落点见 [第 3 章 §3.2.3 激活函数](chapter3/chapter3_语言模型架构和训练技术细节.md) 关于 GeGLU / SwiGLU / ReGLU 的曲线对照，以及 [第 3 章 §3.2.2 前馈网络](chapter3/chapter3_语言模型架构和训练技术细节.md) 的 modern default 骨架讨论。

阅读时把"某模型用了某技巧"换成下面这类问题：

- 这个技巧节省的是 FLOPs、HBM 带宽、显存容量，还是通信？
- 它是在训练、prefill、generation，还是服务调度阶段起作用？
- 它牺牲了什么：表达能力、稳定性、实现复杂度、可复现性，还是硬件可移植性？

## 前言小结

知识地图与术语口径在前文定下之后，[第 1 章 分词器](chapter1/chapter1_分词器.md) 从 Unicode → UTF-8 → BPE → vocab / merges 这条 tokenizer 流水线出发，把分词作为接触文本的第一道接口。字节、压缩率、词表利用率和 round-trip 这几项检查都会回到资源账本和工程取舍上，并为 [第 2 章 PyTorch 与资源核算](chapter2/chapter2_pytorch与资源核算.md) 的训练 FLOPs 粗估 $6 \times N_{\text{data}} \times N_{\text{param}}$ 做准备——其中 $N_{\text{param}}$ 是非 embedding 参数量， $N_{\text{data}}$ 是训练 token 数，token 化方式直接决定 $N_{\text{data}}$ 这一侧的账。
